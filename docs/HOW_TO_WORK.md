# วิธีทำงานประจำวัน — อ่านอันนี้ก่อนเริ่ม

> เอกสารนี้ตอบคำถามเดียว: **"วันนี้ผมทำอะไร และทำเสร็จแล้วรู้ได้ยังไงว่าถูก"**
>
> ถ้าอ่านจบแล้วยังตอบไม่ได้ แปลว่าเอกสารนี้ยังไม่ดีพอ — บอกมาแล้วจะแก้

## เริ่มยังไง ถ้าเพิ่งเข้าโปรเจกต์

### 1. ตั้งเครื่องให้เสร็จก่อน

ทำตาม [`../INSTALL.md`](../INSTALL.md) จนกว่าคำสั่งนี้จะเขียว:

```bash
python tools/check_all.py --with-tests
```

### 2. ติดตั้งตัวตรวจอัตโนมัติ ครั้งเดียวต่อเครื่อง

```bash
python tools/check_all.py --install-hook
```

ตั้งแต่นี้ทุกครั้งที่ `git commit` จะมีตัวตรวจว่าไม่มี secret หรือข้อมูลส่วนตัวหลุด

> `.git/hooks/` ไม่ขึ้น git — **ทุกคนต้องรันคำสั่งนี้เองคนละครั้ง**

### 3. เปิดลิงก์นี้ แล้ว bookmark ไว้

```text
https://github.com/boss2912/luma-webapp-g04/issues/assigned
```

**นี่คือหน้าเดียวที่ต้องดูทุกวัน** — เห็นเฉพาะงานของตัวเอง

### 4. เปิดไฟล์ "เริ่มตรงนี้" ของตัวเอง

หน้า issue ข้างบนบอกว่า**มีงานอะไร** แต่ไม่ได้บอกว่า**หยิบอันไหนก่อน** — อันนั้นอยู่ในไฟล์ของแต่ละคน

| คุณคือ | เปิดไฟล์นี้ |
|---|---|
| คนที่ 1 · Web Platform | [`START_1_WEB.md`](START_1_WEB.md) |
| คนที่ 2 · Data & Storage | [`START_2_DATA.md`](START_2_DATA.md) |
| คนที่ 3 · AI + Image Processing | [`START_3_AI_IP.md`](START_3_AI_IP.md) |

ในนั้นมีคิวงานเรียงลำดับ · งานวันแรกแบบทีละขั้น · และบอกว่า**ใครกำลังรองานของคุณอยู่**

## งานถูกจัดไว้ 3 ชั้น

| ชั้น | คืออะไร | ทำยังไงกับมัน |
|---|---|---|
| **Milestone** | เวอร์ชันที่ส่ง — M0 · V2 · IP · V3 · V4 · V5 | ดูว่าตอนนี้อยู่ตรงไหน เหลืออีกกี่งาน |
| **Epic** 📦 | ก้อนงานใหญ่ เช่น "หน้าเว็บทั้งหมด" | **ห้ามลงมือทำที่นี่** ใช้ดูภาพรวมอย่างเดียว |
| **Task** | งาน 1–2 วัน มีเงื่อนไขความสำเร็จชัด | **หยิบอันนี้ไปทำ · 1 task = 1 PR** |

Epic จะปิดเองเมื่องานย่อยครบ และ GitHub แสดง % ความคืบหน้าให้อัตโนมัติ

### วิธีเลือกว่าจะทำอันไหน

1. เปิด **ไฟล์ `START_*.md` ของตัวเอง** (ตารางในข้อ 4 ข้างบน)
2. หยิบ**อันบนสุดของคิวที่ยังไม่ปิด** แล้วเริ่มได้เลย
3. ถ้าแถวนั้นมี 🟡 หรือ 🔴 อยู่ แปลว่ามีเงื่อนไขต้องอ่านก่อน — ในตารางบอกไว้ว่ารออะไร

> ⚠️ **GitHub บอกลำดับงานให้ไม่ได้** — repo นี้ไม่มี label `Blocked` และ GitHub บันทึกได้แค่
> ความสัมพันธ์ epic → sub-issue กับ blocked-by ของบาง issue เท่านั้น
> ส่วน "ลำดับที่ควรทำ" และ "คนไหนกำลังรอเราอยู่" ถูกเขียนไว้ใน `START_*.md` ที่เดียว
>
> ถ้าลำดับในนั้นไม่ตรงกับความจริงแล้ว **แก้ไฟล์นั้น** อย่าปล่อยให้ค้าง

ถ้าเลือกไม่ได้จริงๆ ให้ดู label `priority:high` ก่อน

## เริ่มงาน 1 อัน

```bash
git checkout develop
git pull
git checkout -b feat/สิ่งที่ทำสั้นๆ
```

แล้วคอมเมนต์ใน issue ว่า "เริ่มทำแล้ว" เพื่อให้คนอื่นรู้ว่าไม่ต้องมาแตะ

### ระหว่างทำ

- commit ย่อยๆ บ่อยๆ ดีกว่า commit ใหญ่ครั้งเดียว
- **ดึง `develop` เข้ากิ่งตัวเองอย่างน้อยสัปดาห์ละครั้ง**

  ```bash
  git fetch && git merge origin/develop
  ```

  กิ่งที่แยกไป 2 สัปดาห์โดยไม่ดึง = ชนกันมหาศาลตอน merge
  นี่คือสาเหตุอันดับหนึ่งของ conflict ที่แก้ยาก

- **ติดเกิน 30 นาที ให้ถาม** อย่านั่งงมเอง — นี่คือข้อที่คนทำผิดบ่อยที่สุด

### ระหว่างรอคนอื่น ให้ใช้ตัวปลอม

ไม่ต้องรอให้ของจริงเสร็จ:

```bash
python tools/mock_forge_server.py
```

Forge ปลอมนี้ตอบเหมือนของจริงทุกอย่าง แต่ไม่ต้องมีการ์ดจอ
ตั้งใน `services/backend/instance/config.py`:

```python
AI_ENGINE_URL = "http://127.0.0.1:7860"
```

ถ้าต้องรอ API ของเพื่อน ก็เขียนข้อมูลปลอมไว้ในไฟล์ JS ก่อนได้เหมือนกัน
**ขอแค่ตกลงรูปแบบ JSON กันไว้ใน [`API_CONTRACT.md`](API_CONTRACT.md) แล้ว** จะได้ไม่ต้องรื้อทีหลัง

## ทำเสร็จแล้วรู้ได้ยังไงว่าถูก

ทุก task มีหัวข้อ **"เงื่อนไขความสำเร็จ"** อยู่ในตัว issue เอง
นั่นคือคำตอบของคำถามนี้

| คำ | แปลว่า |
|---|---|
| **MUST** | ไม่ทำ = ยังไม่เสร็จ ปิด issue ไม่ได้ |
| **MAY** | มีก็ดี ไม่มีก็ปิด issue ได้ |

### ลำดับที่ถูก

```text
อ่านเงื่อนไขในissue -> แปลงเป็น test -> เขียนโค้ดให้ test ผ่าน -> ติ๊กช่อง
```

**ไม่ใช่** เขียนโค้ดเสร็จแล้วค่อยนึกว่าจะทดสอบอะไร

ถ้าเขียน test จากเงื่อนไข จะได้ test ที่ตรงกับสิ่งที่ผู้ใช้ต้องการจริง
ถ้านึกเอาทีหลัง จะได้ test ที่ยืนยันแค่ว่า "โค้ดทำสิ่งที่โค้ดทำ" ซึ่งไม่มีประโยชน์

### ตัวอย่าง — จากเงื่อนไข 1 ข้อ เป็น test 1 ตัว

เงื่อนไขใน issue:

> **MUST** ล็อกอินเป็นคนอื่นแล้วต้องไม่เห็นภาพของเรา แม้จะรู้ id (ต้องได้ 404 ไม่ใช่ 403)

แปลงเป็น test:

```python
def test_ดูภาพของคนอื่นไม่ได้(client):
    ภาพของ_a = สร้างผู้ใช้และภาพ("a@example.com")
    เข้าสู่ระบบ(client, "b@example.com")

    resp = client.get(f"/api/assets/{ภาพของ_a.id}/image")

    assert resp.status_code == 404      # ไม่ใช่ 403
```

### ควรเขียน test แค่ไหน

ไม่ต้องไล่ตาม coverage เอาที่คุ้มที่สุดก่อน:

| | |
|---|---|
| ✅ **เขียนแน่นอน** | สิทธิ์การเข้าถึง (ใครเห็นอะไรได้) · การตรวจ input · ฟังก์ชันคำนวณที่รู้คำตอบล่วงหน้า (เช่น `gamma(img, 1.0)` ต้องได้ภาพเดิม) |
| 🟡 **เขียนถ้าไหว** | เส้นทางหลัก 1 เส้นครบวงจร: สมัคร → สร้างภาพ → เห็นในแกลเลอรี |
| ❌ **ไม่ต้องเขียน** | CSS ตำแหน่งปุ่ม ความสวยงาม สิ่งที่ตาดูแล้วรู้ทันที |

**กฎที่คุ้มที่สุด**: bug ที่เคยหลุดแล้ว ให้เพิ่ม test 1 ตัว**ก่อน**แก้เสมอ
จะได้ไม่กลับมาอีก — ดูรายการ F01–F15 ใน [`../archive/SECURITY_FIXES_v1.md`](../archive/SECURITY_FIXES_v1.md)

```bash
python tools/run_all_tests.py
```

## ส่งงาน

```bash
python tools/check_all.py --with-tests    # ต้องเขียวก่อน
git push -u origin ชื่อกิ่งของคุณ
```

เปิด PR → แม่แบบจะขึ้นมาเอง ติ๊ก checklist ให้ครบ

ใส่ `Closes #45` ในคำอธิบาย PR แล้ว GitHub จะปิด issue ให้เองตอน merge

### Definition of Done — ใช้กับทุก issue เหมือนกันหมด

ต่างจาก "เงื่อนไขความสำเร็จ" ตรงที่อันนั้นเฉพาะของแต่ละ issue ส่วนอันนี้ใช้ร่วมกัน:

- [ ] เงื่อนไขความสำเร็จติ๊กครบทุกข้อที่เป็น **MUST**
- [ ] `python tools/check_all.py --with-tests` เขียว
- [ ] มีคนอื่นรีวิว PR แล้วอย่างน้อย 1 คน
- [ ] ถ้าเปลี่ยนรูปแบบ API → แก้ [`API_CONTRACT.md`](API_CONTRACT.md) แล้ว และบอกคนที่เกี่ยวข้อง
- [ ] merge เข้า `develop` แล้วระบบยังรันได้

### ขนาด PR

**ไม่เกินประมาณ 400 บรรทัด** ถ้าเกินให้ซอยเป็นสอง PR

ไม่ใช่กฎที่ตั้งขึ้นมาลอยๆ — งานวิจัยพบว่า PR เกิน 1,000 บรรทัด
อัตราการเจอ bug **ตกลง 70%** เพราะคนรีวิวหมดสมาธิ กดผ่านเพราะเหนื่อย ไม่ใช่เพราะมั่นใจ
(ดู [`INDUSTRY_PRACTICES.md`](INDUSTRY_PRACTICES.md))

## รีวิวงานคนอื่น

- **รีวิวภายใน 1 วัน** — PR ที่ค้าง 3 วันจะ conflict จนต้องเขียนใหม่
- **แยกให้ออกระหว่าง "ผิด" กับ "ฉันจะเขียนอีกแบบ"** — อย่างหลังพูดได้ แต่ไม่ควรบล็อก PR
- เจอโค้ดที่ดีก็ชมด้วย รีวิวที่มีแต่คำติทำให้คนกลัวการส่ง PR
- ดูเงื่อนไขความสำเร็จใน issue ประกอบ ไม่ใช่ดูแค่โค้ด

### กฎเดียวที่ต้องจำ

| โฟลเดอร์ | เจ้าของ |

| `services/database/` | คนที่ 2 |

### ไฟล์ที่เป็นของทุกคน — ต้องคุยก่อนแก้

- [`API_CONTRACT.md`](API_CONTRACT.md) — สัญญาระหว่าง service
- [`DECISIONS.md`](DECISIONS.md) — บันทึกการตัดสินใจ
- `tools/` · `.github/`

**การแก้สัญญาฝ่ายเดียวคือต้นเหตุของบั๊กแบบ "ฝั่งหนึ่งส่ง array อีกฝั่งรอ string"**
ซึ่งกว่าจะรู้ตัวก็ตอนต่อระบบเข้าด้วยกันแล้ว

### บทเรียนจริงจาก v1

`tests/conftest.py` ถูกสร้างพร้อมกันใน 2 กิ่ง แล้วชนกันตอน merge

ซึ่งช่วยได้จริง — **แต่ที่ดีกว่าคือตกลงตั้งแต่ต้นว่าใครเป็นเจ้าของไฟล์นั้น**

## นัดคุยกันสัปดาห์ละครั้ง — 15–30 นาที

ได้ผลกว่าเครื่องมือทุกตัวรวมกัน

1. แต่ละคนหยิบ issue ของตัวเอง **ไม่เกิน 2 อัน**
   (คนที่หยิบ 5 อันพร้อมกัน = ไม่เสร็จสักอัน แล้วไม่มีใครกล้าไปแตะเพราะเป็นของเขา)
2. พูดออกมาว่าสัปดาห์นี้จะแตะไฟล์ไหน — ประโยคเดียวสั้นๆ
   *"อาทิตย์นี้ผมจะรื้อ auth นะ"* ป้องกัน conflict ได้มากกว่าเครื่องมือใดๆ
3. มีอะไรกระทบ `API_CONTRACT.md` **คุยตอนนี้** ไม่ใช่ตอนเขียนโค้ดไปครึ่งทาง
4. ใครติดอะไรอยู่ ใครรอใคร

> **ข้อตกลงที่พูดกันเฉยๆ หายไปใน 3 วัน** — ตกลงอะไรได้ เขียนลงไฟล์ทันที

## ถ้าเวลาไม่พอ ตัดอะไรก่อน

**ตัดได้** (เรียงจากตัดก่อน): LLM แปลง prompt → image-to-video → Regional Prompt →
LoRA → ControlNet → V5 Nginx → V4 แยก frontend

**ตัดไม่ได้เด็ดขาด**

- ❌ pipeline 5 ส่วน — เป็นเกณฑ์ให้คะแนนโดยตรง **40% ของวิชา**
- ❌ ข้อ 5 การวัดผล — เป็นข้อที่มักถูกลืมและอาจารย์ระบุไว้ชัด
- ❌ Asset Hub ที่ค้นหาได้จริง
- ❌ Auth ที่ปลอดภัย — เคยมีช่องโหว่ 15 ข้อ อย่าให้ซ้ำ

> V4/V5 เป็นเรื่อง deployment ที่พูดในรายงานได้ว่า "ออกแบบรองรับไว้แล้ว"
> แต่ pipeline 5 ส่วนพูดแทนไม่ได้ ต้องมีโค้ดและตัวเลขจริง
